# 全量排行查询优化记录

## 实测问题

正式版本包含20711042行entity_daily；数据约5.0GiB、原索引约1.6GiB，数据库buffer pool为256MiB。完整观察期商品浏览排行在无其他重任务时，优化器默认计划及强制已有二级索引计划均被5秒语句限时中止（MariaDB错误1969）。证据为`var/production/entity-query-steady-baseline.json`。浏览器商品页真实显示依赖错误，不能算页面验收通过。

## 优化约束

保留API的日期范围、完整候选人口、计数、字符串ID排序及签名游标语义。不能延长在线五秒时限，不能把单日TopK的局部计数相加冒充区间排行，也不能只支持默认完整观察期。先验证既有索引，确认不足后才增加一个覆盖索引，不另存45个日期范围的大量重复聚合行。

迁移006增加`(release_id,entity_type,behavior_type,date,event_count DESC,entity_id ASC)`索引。原索引和业务数据保留。大表迁移前做一致性快照；已初始化数据库持有同一重任务租约，使用有界维护时限，避免与训练或规模作业争抢资源。初始空库在租约表创建前也使用同名数据库锁。

## 精确算法及停止条件

1. 从查询区间每一天的排序流中读取一小批ID，日期、类型和行为均使用相同口径。
2. 对所有新候选，利用主键查询区间内每一天的完整计数并求和。只读到候选的某一天不会遗漏其他天的贡献。
3. 某一天尚未读取的记录，其计数不大于该天最后读到的计数；该天读完则上界为0。将每天的上界相加，得到任何尚未成为候选的ID在整个区间内可能达到的最大分数。
4. 只有当前所需最后一名候选的完整总数严格大于这个上界，才能证明未知ID不能进入结果并停止。相等时继续读取，避免同分时ID排序错误；所有流读完时返回完整精确排序。
5. 下一页先按签名游标的计数及ID排除已返回区间，仍以同样上界证明本页结果。多读取一条用于判断has_more。

时间预算4.5秒分配到所有SQL及连接池等待，单个请求不会获得多次独立五秒预算。候选数量也有上限；达到时间或内存预算时明确失败，不返回冒充完整排行的部分结果。极端均匀分布或很深的分页可能无法提前剪枝，仍需报告实际适用边界。

## 验证状态

真实隔离MariaDB测试通过：独立完整GROUP BY作为参照，覆盖单日和跨日、商品/类目、浏览/购买、稀疏记录、完整同分集合、字符串ID排序、连续分页及预算失败。刻意使用很小的读取批次强制跨批次证明，日志为`var/production/entity-ranking-contract.log`。
